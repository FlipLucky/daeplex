# T70 — Headless e2e harness for `gui-base`

**Status:** done — shipped
**Touches:** `internal/frontend/gui-base`
**Reads:** G4, G5, G6 (Gio key filters), G20 (substring assertions), G22 (prove it fails first), D8 (frontend parity), D64, D68
**Follows:** T33b

## What and why

`tui-base` has driven real frames through a real `tcell.SimulationScreen`
since 2026-10-31. `gui-base` had nothing — every shared feature was
verified on one frontend and build-checked on the other.

T33b made the cost of that concrete rather than theoretical. `<C-v>` had
been bound in `keyengine` since T54 and translated by neither frontend, so
block-visual was unreachable in the actual application while every unit
test passed. The tui harness is what caught it; nothing was watching the
GUI side at all. D8 calls frontend divergence a bug, and an asymmetry in
what gets *tested* produces exactly that divergence over time.

## Shape

`Run` kept only what genuinely needs a window — building the context and
submitting the finished ops. Everything a frame does moved into
`(g *GioApp) frame(gtx) (quitRequested bool)`. Same split as
`Boot`/`newApplication` in `tui-base`, for the same reason.

A test then drives real frames with no window at all:

```go
router := new(input.Router)
gtx := layout.Context{Ops: ops, Constraints: layout.Exact(size), Source: router.Source()}
app.frame(gtx)
router.Frame(gtx.Ops)
```

`gioui.org/io/input.Router` is Gio's own event plumbing — the same type its
widget tests use — so an injected `key.Event` travels the production filter
path rather than a test shortcut. That matters more here than it would
elsewhere, because that path is three gotchas deep (G4, G5, G6) and all
three are silent failures: the key simply never arrives.

Focus is not granted until a frame that already claimed the tag has been
submitted (G4), so the harness runs two frames before any test injects a
key. A test that skipped that would see its first keystroke vanish.

## The asymmetry that remains, and why it isn't effort

tcell hands back a grid of cells, so a tui assertion reads the glyphs a
user would see. Gio renders to an ops list bound for a GPU, with no text to
read back. `gioui.org/gpu/headless` exists and would rasterize a real
frame, but it needs a GPU context and produces pixels — asserting "line-001
is on screen" from pixels means OCR, which is not a trade worth making.

So the deepest honest assertion here is on what the frame *consumed*: the
viewport Editor derived, the cursor the keystroke produced, the mode it
landed in. Both failures this harness exists for sit upstream of the
pixels — a key that never reaches the engine, and a frontend that never
reports its metrics — so the limit costs nothing that was being looked for.
Stated plainly rather than papered over: this is not glyph-level
verification and should not be described as such.

## What it covers

| test | guards |
|---|---|
| `HalfPageScrollMovesCursorAndWindow` | both halves of `<C-d>`/`<C-u>` (D68), off a real 800×600 layout |
| `BlockVisualIsReachable` | the T54 gap, on the frontend that never had a guard |
| `InsertEditUndoRendersThroughRealPipeline` | `key.EditEvent` text vs. named `key.Event`, and undo |
| `ViewportRowsFollowWindowSize` | D64's claim that a resize needs no handling of its own |

The last one is the case the terminal cannot express at all: a GUI window
resizes in pixels under a font that can rescale independently, and D64
claims both fall out of one division. Now asserted rather than argued.

**Negative controls (G22)** — each confirmed to fail against deliberately
broken code before being trusted: `<C-d>` un-translated, `<C-v>`
un-translated (the original bug, re-introduced), `SetViewportMetrics` not
called, `<Esc>` un-translated.

## Tried and dropped

- **Headless GPU rasterization + screenshot assertions.** Rejected: needs a
  GPU context, and pixels carry no readable text.
- **A render smoke test that only checks the frame doesn't panic.**
  Rejected: it would have passed throughout the entire period `<C-v>` was
  unreachable.

## State

Shipped. Both frontends now drive real frames through their production
pipelines, so a feature touching both can be verified on both.

Worth knowing for the next one: these tests assert through
`ws.Current()`, so they exercise the Workspace seam too. Extending them to
buffer switching (T60's tui equivalent) needs no new harness.
